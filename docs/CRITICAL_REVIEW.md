# 0. กรอบการวิพากษ์

สถาปัตยกรรมที่ทีมวางไว้ (8 ชั้น + dual-law fail-safe + divide & conquer + multi-agent)
**ครอบคลุมด้าน "การไหลของข้อมูล" ได้ดีมาก** แต่ระบบนี้ไม่ใช่แค่ data pipeline —
มันคือ **ระบบควบคุมความปลอดภัยสาธารณะ (safety-critical public system)**.
เอกสารนี้จึงวิพากษ์ในมิติที่ pipeline ปกติมักมองข้าม

# 1. จุดบอดสำคัญที่ "ยังไม่มี" ในสถาปัตยกรรม

### 1.1 🔴 ความมั่นคงปลอดภัยไซเบอร์ของ "การสั่งไฟ" (Cybersecurity) — ใหญ่สุด
- ระบบนี้ **สั่งไฟจราจรได้** → กลายเป็นเป้าโจมตี. ถ้าถูกแฮก = อันตรายถึงชีวิต/จราจรอัมพาต
- **ยังไม่มีในผัง:** การเซ็นคำสั่ง (signed commands), network segmentation (แยกวง OT/IT),
  mutual TLS, anti-replay, ตรวจจับคำสั่งผิดปกติ, hardware security ที่ PLC
- **Adversarial AI:** สติกเกอร์/แผ่นป้ายหลอก YOLO (adversarial patch), spoof กล้อง → ต้องมี sanity check + sensor fusion
- **ต้องเพิ่ม:** Security layer เฉพาะการ actuate + threat model + pen-test ก่อน deploy

### 1.2 🔴 มาตรฐาน/การรับรอง + เขตอำนาจ (Regulatory & Jurisdiction)
- สัญญาณไฟจราจรเป็น **อุปกรณ์ที่กำกับโดยกฎหมาย** — จะให้ AI คุมต้องผ่านการรับรองความปลอดภัย
- **เขตอำนาจซ้อน:** ถนนบางสายเป็นของ **กรมทางหลวง/แขวงทางหลวง** บางแยกเป็นของ **เทศบาล** บางเรื่องของ **ตำรวจจราจร** → ใครอนุมัติ/รับผิดต่อแยกไหน?
- **ต้องเพิ่ม:** แผนผังเขตอำนาจต่อแยก + กระบวนการขออนุมัติ + มาตรฐานความปลอดภัย (เช่น conflict monitor ที่ผ่านการรับรอง)

### 1.3 🔴 ความรับผิด (Liability) เมื่อเกิดอุบัติเหตุ
- ถ้า AI ปรับไฟแล้วเกิดอุบัติเหตุ — **ใครรับผิด?** เทศบาล (controller)? ผู้พัฒนา? เจ้าหน้าที่ที่กดในโหมด manual?
- **ยังไม่มี:** กรอบความรับผิด + ประกันภัย + log ที่ใช้สืบสวนได้ (black-box/audit ของทุกการตัดสินใจ)
- **ต้องเพิ่ม:** "Decision black-box" บันทึกทุก input→decision เพื่อสอบสวนย้อนหลัง

### 1.4 🟠 Multimodal & ความเป็นธรรม (Equity) — ระบบเอนเอียงไป "รถยนต์"
- ตอนนี้วัด vehicle_count/queue เป็นหลัก → เสี่ยง **optimize เพื่อรถยนต์ ลืมคนเดินเท้า/จักรยาน/รถเมล์**
- **ขาด:** การให้สิทธิ์ **รถฉุกเฉิน (ambulance/ดับเพลิง)**, **รถสาธารณะ (bus priority)**, สิทธิ์คนข้าม, การไม่ "อดอยาก" ถนนสายรอง (fairness constraint)
- **ต้องเพิ่ม:** Emergency Vehicle Preemption (กดล่วงหน้าให้รถฉุกเฉิน), bus priority, reward ที่นับ "person-delay" ไม่ใช่ "car-delay", pedestrian demand

### 1.5 🟠 ระบบ "ทำนาย" + ระดับโครงข่าย (ไม่ใช่แค่แยกเดี่ยว)
- ตอนนี้ reactive + ปรับทีละแยก → ของจริงรถไหลเป็น "คลื่น" ทั้งเส้น
- **ขาด:** โมเดลพยากรณ์ (ST-GNN/TFT) + **green-wave/coordination ทั้ง corridor** + max-pressure ระดับโครงข่าย
- **ต้องเพิ่ม:** ชั้น network-level optimization (ไม่งั้นแก้ที่แยกหนึ่งไปสร้างปัญหาแยกถัดไป)

### 1.6 🟠 จำลองก่อนใช้จริง (Digital Twin / Simulation)
- จะปรับ logic/RL โดยไม่ลองในซิมก่อน = อันตราย
- **ขาด:** SUMO/Aimsun ของถนนขอนแก่นจริง → ทดสอบทุกแผนก่อน deploy + shadow mode
- **ต้องเพิ่ม:** Digital twin เป็น "สนามซ้อม" ของระบบ

### 1.7 🟠 การเชื่อมกับของเดิม (Existing Controller Integration)
- ตู้ไฟเดิมในไทยมีหลายชนิด (fixed-time, ATC, บางที่ SCATS/SCOOT) — Modbus relay อาจไม่พอทุกแบบ
- **ต้องเพิ่ม:** adapter หลายโปรโตคอล + แผนเข้ากันได้กับ controller เดิมแต่ละรุ่น

# 2. จุดบอดเชิง "ปฏิบัติการจริง" (ที่เดโมไม่เห็น)

### 2.1 โหมด Manual "สเกลไม่ได้" จริงหรือ? (วิพากษ์จุดขายตัวเอง)
- จุดขายคือ manual mode ทำให้ครอบคลุมทั้งเมืองในงบถูก — **แต่เจ้าหน้าที่ 1 คนเฝ้าหลายแยกพร้อมกันไม่ได้**
- ความเหนื่อยล้า/ความผิดพลาดมนุษย์ → manual อาจดีแค่ "ช่วงพีค/จุดสำคัญ" ไม่ใช่ทั้งวันทั้งเมือง
- **ต้องคิดใหม่:** manual = "semi-auto" (ระบบทำเอง 90% เจ้าหน้าที่ override เมื่อจำเป็น) + จัดลำดับความสำคัญแยกที่ต้องเฝ้า

### 2.2 ต้นทุน "ดำเนินการต่อเนื่อง" (OPEX) ไม่ใช่แค่ 150k (CAPEX)
- 150,000 บาท/แยก คือค่าติดตั้ง — **แต่ค่าเน็ต/ไฟ/บำรุงรักษา/เปลี่ยนกล้อง/คน ดูแลรายปีล่ะ?**
- กล้อง/Jetson เสีย, ถูกขโมย, ฟ้าผ่า, น้ำท่วม (ขอนแก่นท่วมบ่อย)
- **ต้องเพิ่ม:** โมเดลต้นทุน TCO 5 ปี + แผนบำรุงรักษา + spare parts + SLA

### 2.3 Cold Start + Edge Cases
- วันแรกไม่มีข้อมูลย้อนหลัง → โมเดล ML ยังโง่
- เหตุพิเศษ: **สงกรานต์/งานบุญ/ขบวนแห่/น้ำท่วม/อุบัติเหตุ** — ระบบรับมือยังไง?
- **ต้องเพิ่ม:** fallback ที่ดีช่วง cold start (ใช้ time-of-day plan) + โหมดเหตุการณ์พิเศษ

### 2.4 ความสามารถของหน่วยงานในการดูแล
- เทศบาลมีคน/ทักษะดูแล AI/Kafka/Spark/K8s ไหม? → ถ้าไม่มี ระบบล่มหลังทีมพัฒนาออก
- **ต้องเพิ่ม:** แผนถ่ายทอดความรู้ + ทำให้ดูแลง่าย (managed/อบรม) + เอกสาร runbook

# 3. Pre-Mortem: "ถ้าโปรเจกต์นี้ล้มในปี 1 เพราะอะไร?"

| ความเสี่ยง | เพราะอะไร | วิธีกัน |
|---|---|---|
| ไม่ได้รับอนุมัติให้ AI คุมไฟ | ไม่ผ่านมาตรฐานความปลอดภัย | เริ่มที่ advisory/manual + ขอรับรอง conflict monitor |
| เหตุการณ์ความปลอดภัย → backlash | ไม่มี fail-safe/ความรับผิดชัด | dual-law fail-safe (มีแล้ว) + black-box + ประกัน |
| ถูกแฮกสัญญาณไฟ | ไม่มี security layer การสั่ง | signed commands + network segmentation + pen-test |
| ตัวเลขไม่ดีขึ้นจริง | สมมติฐานผิด/ไม่วัด baseline | pilot วัด before/after + อิสระตรวจสอบ |
| เจ้าหน้าที่ไม่ใช้ manual | workflow เปลี่ยน/ภาระเพิ่ม | semi-auto + UX ดี + อบรม + จัดลำดับแยก |
| งบหมดหลัง pilot | ไม่มีโมเดล OPEX/ผู้สนับสนุน | TCO ชัด + carbon credit/CSR + ขยายทีละโซน |
| ข้อมูลส่วนบุคคลรั่ว/ฟ้อง | PDPA ไม่รัดกุม | DPIA/DPO/consent/audit (มีแผนแล้ว) |
| ระบบล่มหลังทีมออก | หน่วยงานดูแลไม่ไหว | runbook + อบรม + ลดความซับซ้อน |

# 4. 7 อย่างที่ "ควรเพิ่ม" เพื่อให้ Solution แข็งจริง (เรียงความสำคัญ)

1. **Security layer สำหรับการสั่งไฟ** (signed command, segmentation, pen-test) — กันภัยถึงชีวิต
2. **Emergency Vehicle Preemption + Bus Priority** — impact สูง, สร้างความน่าเชื่อถือ, แก้ข้อหา "เอนเอียงรถยนต์"
3. **Digital Twin (SUMO)** — ทดสอบปลอดภัยก่อน + เปิดทาง RL/network optimization
4. **Decision Black-box + กรอบความรับผิด** — สำหรับ liability/audit/สอบสวน
5. **โมเดลพยากรณ์ + network/corridor coordination** — เปลี่ยนจาก reactive → proactive
6. **แผน Jurisdiction + Regulatory approval** — ระบุเจ้าของ/ผู้อนุมัติต่อแยก
7. **TCO 5 ปี + แผนบำรุงรักษา/ถ่ายทอดความรู้** — ความยั่งยืนหลัง pilot

# 5. จุดแข็งที่ "ต้องรักษาไว้" (เพื่อให้สมดุล)
- ✅ **Reuse-first 150k/แยก** = จุดต่างที่ชนะ SCATS/SCOOT เรื่องต้นทุน
- ✅ **Dual-law fail-safe** = คิดเรื่องความปลอดภัยมาดี (ต่อยอดเป็น security ได้)
- ✅ **Hybrid Auto/Manual** = ขยายได้จริง (ถ้าปรับเป็น semi-auto)
- ✅ **Edge-only/metadata** = ดีต่อ PDPA + แบนด์วิดท์ตั้งแต่ออกแบบ
- ✅ **Open-source/self-host** = เมืองเป็นเจ้าของข้อมูล ไม่ lock-in

# 6. สรุป (Critical takeaway)

ไอเดียนี้ **แข็งแรงในฐานะ "ระบบข้อมูล + ปรับไฟอัจฉริยะต้นทุนต่ำ"** — สถาปัตยกรรมครบ.
แต่ในฐานะ **"ระบบควบคุมความปลอดภัยสาธารณะจริง"** ยังขาด 3 เสาหลัก:
**(1) ความปลอดภัยไซเบอร์ของการสั่งไฟ · (2) ความเป็นธรรม/multimodal (ฉุกเฉิน-รถเมล์-คนเดิน) ·
(3) ธรรมาภิบาล/ความรับผิด/การรับรอง**.

> เพิ่ม 3 เสานี้ + พยากรณ์/ซิม/TCO → จาก "เดโมที่น่าประทับใจ" กลายเป็น "ระบบที่ deploy จริงได้อย่างรับผิดชอบ"

*Urban IntelliFlow — จราจรอัจฉริยะ เมืองน่าอยู่ ขอนแก่นยั่งยืน*
