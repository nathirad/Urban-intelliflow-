# ส่วนที่ 1 — PDPA: ระบบนี้ "เสี่ยงผิดกฎหมายตรงไหนบ้าง"

อ้างอิง: พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 (PDPA). ระบบเรามีกล้อง CCTV +
AI + เก็บประวัติการเดินทางผู้ใช้ → แตะ "ข้อมูลส่วนบุคคล" หลายจุด. มาวิเคราะห์ทีละความเสี่ยง:

### 1.1 ภาพจากกล้อง = ข้อมูลส่วนบุคคล
- **ใบหน้า + ป้ายทะเบียนรถ** ระบุตัวบุคคลได้ → เป็นข้อมูลส่วนบุคคลตาม ม.6
- **ความเสี่ยง:** ถ้าบันทึก/ประมวลผลโดยไม่มี *ฐานทางกฎหมาย* (lawful basis) = ผิด ม.19
- **ทางแก้ของเรา:** Edge ประมวลผลในกล่อง ส่งออกเฉพาะ *ตัวเลข* (count/queue/score) ไม่ส่งภาพดิบ →
  ลดการ "เก็บ/เปิดเผย" ข้อมูลส่วนบุคคลลงมาก. แต่ *ระหว่างประมวลผล* ในกล่องก็ยังถือว่า "เก็บ" ชั่วคราว

### 1.2 ฐานทางกฎหมายที่ใช้ได้ (และข้อควรระวัง)
- การขอ *ความยินยอม* (consent, ม.19) จากคนขับทุกคนบนถนน = **เป็นไปไม่ได้จริง**
- หน่วยงานรัฐใช้ฐาน **"ภารกิจของรัฐ/อำนาจหน้าที่"** (ม.24(4)(5)) หรือ **ประโยชน์โดยชอบด้วยกฎหมาย** ได้
- **ข้อควรระวัง (Critical):** ฐานนี้ต้อง *ได้สัดส่วน (proportionate)* — เก็บเท่าที่จำเป็นต่อ "จัดการจราจร" เท่านั้น
  ถ้าเอาไปทำเกินวัตถุประสงค์ (เช่น สอดส่องบุคคล) จะหลุดจากฐานทันที

### 1.3 จุดเสี่ยงสูงสุด: "ประวัติการเดินทางของผู้ใช้แต่ละคน"
- การเก็บว่า *ใคร ไปไหน เมื่อไหร่* = **การทำโปรไฟล์การเคลื่อนไหว (movement profiling)** ความเสี่ยงสูงมาก
- ต้องใช้ฐาน **ความยินยอมโดยชัดแจ้ง (explicit consent, ม.19)** + ถอนได้ทุกเมื่อ (ม.19 วรรคห้า)
- **ผิดได้ตรงไหน:** เก็บโดยไม่ขอ consent / ถอน consent แล้วยังเก็บ / เอาไปใช้ต่อโดยไม่แจ้ง
- **ทางแก้ของเรา:** ผูกกับบัญชี (opt-in), แสดง PDPA notice ในแอป, ให้สิทธิ์ลบ, ไม่เก็บพิกัดบ้าน/ที่ทำงานละเอียด

### 1.4 ข้อมูลอ่อนไหว (Sensitive Data, ม.26)
- ใบหน้า → ถ้าทำ *Facial Recognition / biometric* = **ข้อมูลชีวมิติ** ต้องฐานเข้มกว่าปกติ (ม.26)
- **Critical:** ระบบเรา **ไม่ทำ face recognition** (แค่นับรถ) → หลีกเลี่ยงความเสี่ยงนี้โดยออกแบบ. ถ้าวันหน้าจะเพิ่ม ต้องทำ DPIA ใหม่

### 1.5 หลักการที่ต้องไม่ละเมิด (และจุดพลาดที่พบบ่อย)
| หลักการ PDPA | มาตรา | ระบบเสี่ยงผิดตรงไหน | ทางแก้ |
|---|---|---|---|
| แจ้งเตือน (Notice) | ม.23 | ไม่มีป้าย "บริเวณนี้บันทึกภาพ" ที่แยก | ติดป้าย + privacy notice ออนไลน์ |
| จำกัดวัตถุประสงค์ | ม.21 | เอาข้อมูลจราจรไปใช้จับผิด/สอดส่อง | ล็อก scope, แยกระบบ, audit |
| เก็บเท่าที่จำเป็น/ลบ | ม.37(1) | เก็บวิดีโอดิบนานเกิน | retention policy, ภาพดิบ transient |
| เปิดเผย/แชร์ข้ามหน่วย | ม.27 | ส่งให้ตำรวจ/หน่วยอื่นโดยไม่มีฐาน | DPA/MOU + ฐานชัดเจน + log |
| สิทธิเจ้าของข้อมูล | ม.30-36 | ไม่มีช่องขอเข้าถึง/ลบ/คัดค้าน | self-service ในแอป |
| ความมั่นคงปลอดภัย | ม.37(1) | ไม่เข้ารหัส/ไม่มี RBAC | TLS, encryption at rest, RBAC, audit |
| แจ้งเหตุละเมิด | ม.37(4) | ข้อมูลรั่วไม่แจ้งใน 72 ชม. | incident response + แจ้ง สคส. |
| มี DPO | ม.41 | monitoring วงกว้างแต่ไม่มี DPO | แต่งตั้ง DPO |

### 1.6 สิ่งที่ "ต้องทำเพิ่ม" เพื่อให้ถูก PDPA จริง
1. **ทำ DPIA** (Data Protection Impact Assessment) ก่อน deploy — เพราะเป็น *systematic monitoring วงกว้าง*
2. **แต่งตั้ง DPO** + ขึ้นทะเบียนกิจกรรมประมวลผล (RoPA)
3. **ป้ายแจ้ง + Privacy Notice** ทุกแยก/ในแอป (ภาษาเข้าใจง่าย)
4. **Consent flow** สำหรับฟีเจอร์ที่ระบุตัวตน (trip history, GPS) + ปุ่มถอน/ลบ
5. **Retention + Auto-delete** (เช่น metadata 90 วัน, ภาพดิบไม่เก็บ/เก็บ <24 ชม.)
6. **Anonymize/Pseudonymize** ก่อนวิเคราะห์ (hash id, blur ป้ายทะเบียนถ้าจำเป็นต้องเก็บภาพ)
7. **Data Sharing Agreement** ถ้าจะส่งให้ตำรวจ/หน่วยงานอื่น
8. **RBAC + Audit log** ทุกการเข้าถึง (ใครดูอะไรเมื่อไหร่)

> **สรุป critical thinking:** ระบบ "ไม่ผิดโดยอัตโนมัติ" — ความผิดเกิดจาก *วิธีใช้* ไม่ใช่ตัวเทคโนโลยี.
> จุดเสี่ยงสุดคือ (ก) ประวัติการเดินทางผู้ใช้ และ (ข) การนำข้อมูลไปใช้เกินวัตถุประสงค์/แชร์ข้ามหน่วย.
> การออกแบบ "edge-only + metadata + ไม่ทำ face recognition" ของเราช่วยลดความเสี่ยงตั้งแต่ต้นทาง (Privacy by Design, ม.37).

# ส่วนที่ 2 — YOLO Self-Optimization (โมเดลปรับปรุงตัวเองจากข้อมูล)

เป้าหมาย: ให้ YOLO26 ที่แต่ละแยก *เก่งขึ้นเรื่อย ๆ* กับสภาพจริงของขอนแก่น
(มอเตอร์ไซค์เยอะ, กลางคืน, ฝนตก, รถพ่วง) โดยใช้ข้อมูลที่เก็บได้ — แบบประหยัดและเคารพ PDPA

### 2.1 Active Learning + Hard-Example Mining
- Edge เลือกเฉพาะเฟรมที่ "โมเดลไม่มั่นใจ" (confidence ต่ำ/กล่องซ้อน/track หลุด) → อัปโหลด *เฉพาะ crop เล็ก ๆ* (ไม่ใช่วิดีโอเต็ม) เข้าคิว label
- ลดข้อมูลที่ต้องเก็บ (ดี PDPA) + เน้น train เคสยาก → คุ้มที่สุด

### 2.2 Auto-Labeling จาก ByteTrack (Pseudo-Labels)
- ใช้ความต่อเนื่องของ track: ถ้า ID เดียวถูกตรวจชัดใน 8/10 เฟรม แต่หลุด 2 เฟรม →
  เติม label เฟรมที่หลุดอัตโนมัติ → ได้ training data ฟรีโดยไม่ต้องคนมานั่ง label

### 2.3 Continual / Nightly Fine-Tuning
- งานกลางคืน (Spark batch) รวบรวม hard examples → fine-tune YOLO26 → ทดสอบ → ถ้า mAP ดีขึ้นค่อย deploy
- **Domain adaptation:** ปรับให้เข้ากับกลางคืน/ฝน/มุมกล้องเฉพาะแยก

### 2.4 Model Distillation (Orin → Nano)
- แยกใหญ่ (Orin, yolo26m) เก็บข้อมูล + train โมเดลใหญ่ → *distill* เป็นโมเดลเล็ก (yolo26n) ส่งให้แยกงบ →
  แยกถูกได้ความแม่นใกล้แยกแพง

### 2.5 Federated Learning (เหมาะกับ PDPA)
- แต่ละแยก train ในเครื่องตัวเอง ส่ง *เฉพาะ weight/gradient* (ไม่ส่งภาพ) ไปรวมที่ศูนย์ →
  โมเดลเก่งขึ้นจากทั้งเมือง **โดยภาพไม่เคยออกจากแยก** = privacy-preserving

### 2.6 Auto-Calibration
- ใช้ trajectory ของรถ (จาก ByteTrack) ประเมิน homography อัตโนมัติ → แปลงพิกเซลเป็นเมตร/กม./ชม. แม่นขึ้น โดยไม่ต้องวัดมือ

### 2.7 MLOps Loop (ทำให้ "self-optimize" จริง)
```
เก็บ hard examples → auto/active label → fine-tune (nightly) → eval (mAP, FP/FN)
   → ถ้าดีขึ้น: canary deploy 1 แยก → A/B → rollout
   → ตรวจ data drift (กลางวัน/คืน/ฝน) → trigger retrain
```
- มี **drift detection** (เช่น distribution ของ confidence เปลี่ยน) เป็นตัว trigger ให้ retrain เอง

# ส่วนที่ 3 — ลด "ไฟแดง" ได้อย่างไร (ลด person-delay จริง)

แนวคิดหลัก: ให้เวลาไฟตาม *ดีมานด์จริง* ไม่ใช่ตารางตายตัว — และประสานทั้งเส้นทาง ไม่ใช่แยกเดี่ยว

### 3.1 Demand-Responsive Phasing (พื้นฐานของเรา)
- ขยายไฟเขียวเมื่อคิวยาว, ตัดไฟเขียวเร็วเมื่อรถหมด → ไม่เสียเวลาเขียวให้เลนว่าง
- **ข้ามเฟสที่ไม่มีรถ:** ถ้าเลนไหนไม่มีรถเลย ไม่ต้องให้เขียว → เลนที่มีรถได้แดงสั้นลง

### 3.2 Max-Pressure / Back-Pressure Control (พิสูจน์แล้วทางวิชาการ)
- เลือกเฟสที่ "แรงดันคิว (pressure)" สูงสุด (คิวขาเข้า − คิวขาออกปลายทาง) → ลด delay รวมทั้งโครงข่าย
- กระจายศูนย์ (แต่ละแยกตัดสินเอง) → เหมาะกับสถาปัตยกรรม edge ของเรา

### 3.3 Green Wave / Corridor Coordination
- ตั้ง offset ระหว่างแยกบนถนนเส้นเดียว (มิตรภาพ/ศรีจันทร์) ให้รถวิ่งต่อเนื่องเป็น "คลื่นเขียว" →
  ลดจำนวนครั้งที่ต้องหยุดไฟแดง (Spark batch หา offset ที่ดีสุดต่อช่วงเวลา)

### 3.4 Adaptive Cycle + Pedestrian on-Demand
- ปรับความยาว cycle ตามช่วงเวลา (เช้า/เย็น/ดึก); ไฟคนข้ามให้เฉพาะตอนมีคนกดจริง → ไม่ตัดรอบรถฟรี ๆ

### 3.5 Priority Preemption
- รถฉุกเฉิน/รถเมล์: ขอเขียวล่วงหน้า (signal preemption) → ลดเวลารวมของผู้โดยสารจำนวนมาก

### 3.6 Reinforcement Learning (ขั้นสูง — roadmap)
- เทรน RL agent (state = คิว/ความเร็ว, action = เลือกเฟส, reward = −person-delay) ในซิมูเลเตอร์ (SUMO) →
  deploy แบบ shadow ก่อน → อาจลด delay เพิ่มอีก 10–20% เหนือ rule-based

### 3.7 ตัววัดผล (ต้องเก็บเพื่อพิสูจน์)
- เวลารอเฉลี่ย/คน, จำนวนครั้งหยุดต่อเที่ยว, ความยาวคิวสูงสุด, อัตราการระบาย (throughput) — เทียบ before/after

# สรุป (Brainstorm → Action)

1. **PDPA:** เทคโนโลยีไม่ผิดเอง — ทำ DPIA, DPO, consent (เฉพาะ trip/GPS), notice, retention, RBAC/audit.
   จุดเสี่ยงสุด = ประวัติการเดินทาง + การใช้เกินวัตถุประสงค์. ออกแบบ edge-only/metadata = Privacy by Design.
2. **YOLO self-optimize:** active learning + auto-label (ByteTrack) + nightly fine-tune + federated learning
   + MLOps drift-trigger → โมเดลเก่งขึ้นเองโดยไม่ละเมิดความเป็นส่วนตัว.
3. **ลดไฟแดง:** demand-responsive + max-pressure + green wave + priority + (RL ในอนาคต) วัดผลด้วย person-delay.
